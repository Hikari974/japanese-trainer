## Technical Architecture

### State Management

**Core State Variables:**
- `scrollingState`: Enum (STOPPED, READY, SCROLLING, VALIDATING)
- `currentWordIndex`: Number (0-based index in words array)
- `userInput`: String (current romaji input)
- `validationState`: 'idle' | 'correct' | 'incorrect'
- `autoProgressTimerRef`: useRef (timer cleanup)

**State Machine Flow:**
```
STOPPED → (Start) → READY
READY → (Scroll Starts) → SCROLLING
SCROLLING → (User Validates) → VALIDATING
VALIDATING → (Correct + Delay) → READY → SCROLLING (next word)
VALIDATING → (Incorrect) → READY → SCROLLING (same word)
ANY → (Stop) → STOPPED
```

### Component Integration

**ScrollingText Component:**
- Receives difficulty-based parameters:
  - Easy: speed 0.5, fontSize 60
  - Normal: speed 0.8, fontSize 48
  - Hard: speed 1.2, fontSize 36
- Controlled by scrollingState (start/stop)

**Romaji Keyboard:**
- 46 buttons (a-n, vowels + consonants)
- Grid layout (5 rows × 10 columns max)
- Disabled during STOPPED state
- Appends characters to userInput

## Technical Decisions

### Decision 1: Mock Words System

**Choice:** Hardcoded 3 words (にほんご, こんにちは, ありがとう)
**Alternatives:** External API, JSON file, database

**Rationale:**
- POC/MVP scope (validate training flow first)
- No external dependencies yet
- Easy to replace later (mockWords array)
- Sufficient for testing UX

**Future:** Replace with dynamic word database (API or local JSON)

### Decision 2: Flexible Romaji Validation

**Choice:** Accept common variations (shi/si, tsu/tu, chi/ti, fu/hu)
**Alternatives:** Strict validation (one correct answer only)

**Rationale:**
- User-friendly (multiple correct romanization systems)
- Matches real-world learning (Hepburn vs Nihon-shiki)
- Reduces frustration (both answers valid)

**Implementation:** normalizeRomaji function (converts to canonical form)

### Decision 3: Auto-Progression on Correct Answer

**Choice:** 1-second delay, then auto-advance to next word
**Alternatives:** Manual "Next" button, immediate progression

**Rationale:**
- UX: Reduces clicks (faster flow)
- Feedback: 1s delay provides visual confirmation (green border visible)
- Balance: Not too fast (user can see result), not too slow (no waiting)

**Risk Mitigation:** Timer cleanup on unmount (memory leak prevention)

### Decision 4: State Machine Architecture

**Choice:** Explicit states (STOPPED, READY, SCROLLING, VALIDATING)
**Alternatives:** Boolean flags, implicit state

**Rationale:**
- Clarity: Explicit states easier to reason about
- Correctness: Prevents invalid state combinations
- Maintainability: Easy to add new states later
- Testing: Clear state transitions to test

**Trade-off:** Slightly more verbose code, but much safer
