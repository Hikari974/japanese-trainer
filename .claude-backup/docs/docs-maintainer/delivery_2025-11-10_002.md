## Executive Summary

Implementation of **persistent user preferences** with local storage using AsyncStorage. The system saves and restores the last selected level and difficulty, providing a seamless user experience across app sessions. The solution is 100% local (offline-first), requires no backend, and is fully tested with 100% coverage.

---

## What Was Implemented

### Feature: User Preferences Persistence

The application now remembers user choices between sessions:
- **Last Level Selected**: Kana, N5, N4, N3, N2, or N1
- **Last Difficulty Selected**: Easy, Normal, or Hard
- **Storage**: Local device storage (iOS/Android) via AsyncStorage
- **Offline-First**: No server required, works 100% offline

### User Experience

**Before:**
- User opens app → must select level and difficulty every time
- No memory of previous choices
- Repetitive interaction

**After:**
- User opens app → last choices automatically pre-selected
- Seamless experience
- Time savings on every session start

## Technical Decisions

### Decision 1: AsyncStorage vs Alternatives

**Choice:** AsyncStorage
**Alternatives Considered:** SQLite, MMKV, FileSystem

**Rationale:**
- Official Expo SDK 52 support
- Simple key-value storage (perfect for preferences)
- Lightweight (no DB overhead)
- Cross-platform (iOS + Android)
- Well-tested and maintained
- Built-in JSON support

### Decision 2: When to Save Preferences

**Choice:** On "Start Session" button click
**Alternatives Considered:** On every change, on app background

**Rationale:**
- Clear user intention (starting session)
- Avoids excessive writes
- Guarantees persistence before navigation
- Performance: Only 1 write per session start

### Decision 3: When to Load Preferences

**Choice:** On HomeScreen mount (useEffect)
**Alternatives Considered:** On app start, lazy loading

**Rationale:**
- Immediate UI feedback (no delay)
- React lifecycle integration (useEffect)
- Automatic on every home screen visit
- No manual trigger needed

### Decision 4: Service + Hook Architecture

**Choice:** Separate service layer + React hook
**Alternatives Considered:** Hook only, Context API

**Rationale:**
- **Separation of Concerns:** Storage logic isolated from React
- **Testability:** Service can be unit tested independently
- **Reusability:** Service can be used outside React components
- **Extensibility:** Easy to add stats persistence later

### Decision 5: Error Handling Strategy

**Choice:** Graceful fallback to defaults on all errors
**Alternatives Considered:** User error messages, retry logic

**Rationale:**
- User-friendly: No error messages for storage issues
- Resilient: App never crashes due to storage
- Simple: One consistent fallback strategy
- Logged: Errors logged for debugging (console.error)
