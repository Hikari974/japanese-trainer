## Technical Decisions

### 1. Migration Strategy
**Decision:** Non-destructive, idempotent migration on first load

**Rationale:**
- Preserves existing user statistics (no data loss)
- Handles both new and existing users gracefully
- Safe to run multiple times (no side effects)
- Automatic trigger ensures no manual intervention needed

**Alternatives Considered:**
- Manual migration script: Rejected (poor UX, requires user action)
- Database versioning: Rejected (overkill for AsyncStorage)

### 2. Cache Implementation
**Decision:** In-memory cache with 5-second TTL, automatic invalidation

**Rationale:**
- Reduces AsyncStorage reads from O(n) UI renders to O(1) per 5 seconds
- 5-second TTL balances performance vs staleness risk
- Automatic invalidation ensures write consistency
- No external cache library needed (simple implementation)

**Alternatives Considered:**
- React state cache: Rejected (component unmount clears cache)
- Longer TTL (30s): Rejected (higher staleness risk)
- No cache: Rejected (performance issue identified in Code Review)

### 3. Data Structure Choice
**Decision:** `unlockedLevels: JLPTLevel[]` + `levelUnlockDates: Record<JLPTLevel, string>`

**Rationale:**
- Array for unlocked levels: Easy iteration, UI rendering, order preservation
- Record for dates: O(1) lookup by level
- Separate structures optimize for different access patterns
- ISO 8601 strings: Future-proof, timezone-aware, sortable

**Alternatives Considered:**
- Single Record<JLPTLevel, { unlocked: boolean, date: string }>: Rejected (redundant boolean)
- Unix timestamps: Rejected (ISO 8601 more readable, standard)

### 4. Default Unlock State
**Decision:** Kana unlocked by default for new users

**Rationale:**
- Aligns with Epic-006 requirement: "Sequential unlock Kana → N5 → N4 → N3 → N2 → N1"
- Kana is entry point for learning progression
- Prevents locked-out state for first-time users
- Enables immediate training session access
